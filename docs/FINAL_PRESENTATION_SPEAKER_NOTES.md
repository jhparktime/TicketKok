# CouponKok 최종발표 발표자 노트

이 문서는 `최종발표.pdf`의 22개 슬라이드를 발표자가 직접 설명하고 질의에 답할 수 있도록 정리한 자료이다. 발표에서는 아래 표기 원칙을 지킨다.

- **구현·검증됨**: 현재 저장소의 코드와 테스트로 확인한 사항이다.
- **배포 구성됨**: IaC·Cloud Build·Cloud Run 설정 또는 배포 경로가 존재하는 사항이다. 실제 모든 서비스가 운영 트래픽을 받고 있다는 뜻은 아니다.
- **확장 계획**: 조건이 충족되면 전환할 수 있도록 설계했으나, 현재 운영 기능으로 주장하지 않는 사항이다.

가장 중요한 한 문장은 다음과 같다.

> CouponKok에서 생성형 AI는 정보를 구조화하고 근거를 설명하지만, 최종 금액·절약액·가격 기준 순위는 결정론적 Calculator MCP Tool만 확정한다.

---

## 발표 전에 반드시 구분할 사실

1. **추천 API와 ADK의 관계**: 현재 API는 결정론적인 추천 경로를 독립적으로 가진다. ADK는 shadow/explanation 모드에서 선택적으로 검증·설명에 쓰이는 경계가 있다. 따라서 ADK나 Gemini 장애가 났다고 할인액을 추정하거나 임의로 바꾸지 않는다.
2. **Agent와 Tool의 차이**: Agent는 자연어 맥락을 해석하고 다음 작업을 선택·설명한다. Tool은 정해진 입출력 계약으로 조회·계산한다. Calculator는 Agent가 아니라 Tool이다.
3. **개인화의 권한**: Personalization Agent는 별도 동의를 받은 집계 이력(방문 주기, 사용 횟수, 만료 위험)을 읽어 표시 우선순위의 이유만 제공한다. Calculator 입력, 할인 규칙, 최종가를 변경하지 않는다.
4. **실제 바코드와 표시용 바코드**: 실제 교환용 바코드는 기기에서 인식하고 Keychain에 암호화 저장한다. Firestore, Cloud Run, Gemini에는 전송하지 않는다. 쿠폰 원본 이미지도 서버에 저장하지 않는다.
5. **보안 적용 상태**: DLP·Model Armor·App Check를 말할 때 항상 적용 모드를 함께 말한다. App Check는 현재 monitor 모드이며, Model Armor는 리전·정책 지원 범위에 맞춘 전환 구조이다. 이를 전 서비스 enforce 상태라고 과장하지 않는다.
6. **배포 자동화 범위**: GitHub Actions의 자동 범위는 lint, API/MCP 계약, Golden Test, evalset·프롬프트 매니페스트 검증이다. Cloud Build/Cloud Run 후보 배포와 traffic promotion은 사람이 검토·승인하는 별도 경계가 있다. 라이브 ADK/MCP trajectory 평가는 staging에서 수동 실행한다.
7. **Agent Engine**: 현재 서비스 런타임의 주력은 Cloud Run이다. Vertex AI Agent Engine은 멀티에이전트 세션 관리·자동 오케스트레이션 부담이 커지는 시점의 전환 후보이지, 현재 주력 런타임이라고 말하지 않는다.

## 전반 구조를 먼저 이해하기

### 마이크로서비스 아키텍처 → 컨테이너 → CI → CD

CouponKok은 처음부터 서비스를 무한히 쪼갠 완전한 마이크로서비스가 아니라, **책임 경계를 분리한 모듈형 Cloud Run 서비스 구조**이다.

- **iOS 앱**: OCR, 위치 감지, 로컬 알림, 실제 바코드의 로컬 보호, 사용자 확인을 담당한다.
- **Cloud Run API**: Firebase 인증 토큰 검증, 입력 검증, 쿠폰·매장·추천 요청의 조합, Firestore 접근, Calculator 결과 반환을 담당한다.
- **Cloud Run ADK**: Store, Coupon, Benefit, Personalization, Recommendation Agent의 워크플로를 담당한다.
- **Cloud Run MCP**: 매장 탐색, 외부 지도 보완, 공식 혜택 검색, Calculator Tool의 제한된 도구 인터페이스를 제공한다.
- **Store Sync Job**: 공공 매장 데이터를 주기적으로 적재·정규화하는 배치성 책임으로 분리한다.

각 서비스는 독립 Docker 이미지로 빌드한다. 이미지는 Artifact Registry에 digest로 보관하고 Cloud Run이 그 불변 이미지를 실행한다. 이렇게 하면 API 코드 수정이 ADK 이미지에, Agent 프롬프트 변경이 MCP 컨테이너에 의도치 않게 영향을 주지 않는다.

CI는 소스 변경이 안전한지를 검사하는 단계이다. GitHub Actions가 lint, TypeScript build, API/MCP 계약 테스트, Calculator Golden Test, 프롬프트 SHA-256 검증, 평가셋 스키마를 검사한다. CD는 통과한 이미지를 Cloud Build로 만들고 Artifact Registry에 저장한 뒤 후보 Cloud Run revision으로 배포하는 단계이다. 후보 revision의 health check, staging holdout, 사람 승인을 거쳐야 traffic을 전환한다. 문제가 생기면 이전 revision으로 되돌리고, 검증된 RAG index도 함께 유지한다.

### IaC를 어떻게 쓰는가

`infra/terraform`은 사람이 콘솔에서 한 번만 설정하고 잊어버리는 방식을 피하기 위한 선언형 인프라 정의이다. Terraform은 “어떤 GCP 리소스와 권한이 있어야 하는가”를 코드로 선언하고, `plan`으로 실제 환경과 선언의 차이를 먼저 보여 준 뒤 승인된 `apply`로 반영한다.

IaC의 범위는 다음과 같다.

- Cloud Run runtime service account를 API·ADK·MCP별로 분리한다.
- 각 service account에 Firestore, Cloud Storage, Secret Manager 등 필요한 역할만 최소 권한으로 부여한다.
- Secret 값 자체가 아니라 Secret 이름·참조 권한만 코드에 둔다.
- Artifact Registry, 필요한 API, Pipeline bucket, 운영 리소스의 구성을 재현 가능하게 한다.
- `terraform.tfstate`는 민감할 수 있으므로 코드와 별도로 관리하고, Terraform 변수에도 실제 API 키를 넣지 않는다.

IaC가 있다고 해서 모든 배포가 Terraform만으로 자동 수행된다는 뜻은 아니다. **인프라의 원하는 상태는 Terraform, 애플리케이션 이미지의 빌드·배포는 Cloud Build/Cloud Run**이 담당한다.

## 슬라이드별 발표 노트

### 1. Final CouponKok - 표지

**말할 내용**

“안녕하세요. CouponKok은 사용자가 이미 가진 쿠폰, 통신사 멤버십, 지원 카드 혜택을 결제 직전 맥락에서 비교해 주는 신뢰형 혜택 추천 서비스입니다. 오늘은 단순히 AI가 할인액을 말하는 서비스가 아니라, AI의 역할과 계산의 역할을 분리해 신뢰를 설계한 과정을 말씀드리겠습니다.”

**들어올 질문과 답**

- “CouponKok이라는 이름의 의미는 무엇인가?” → 쿠폰을 필요할 때 ‘콕’ 집어 주고, 여러 혜택을 한 번 더 ‘콕’ 확인한다는 사용자 행동을 직관적으로 표현한 이름이다.
- “왜 앱인가?” → 위치·카메라/OCR·로컬 알림·Keychain을 동시에 안전하게 활용해야 하므로 iOS 네이티브 앱이 핵심 경험에 적합하다.

### 2. Problem & Goal - 혜택은 있는데 다 챙기지 못한다

**말할 내용**

“문제는 혜택의 부재가 아니라 정보의 파편화입니다. 통신사, 카드, 프랜차이즈, 갤러리와 메신저에 저장된 쿠폰이 서로 다른 화면과 다른 조건으로 존재합니다. 사용자는 매장 앞에서 어떤 쿠폰이 가능한지, 카드·멤버십과 중복되는지, 한도와 최소 주문금액을 충족하는지를 직접 기억하고 계산해야 합니다. 이 과정에서 시간 비용과 혜택 누락이 생깁니다. 또한 AI가 계산과 설명을 함께 하면 숫자의 근거를 사용자가 검증하기 어렵습니다.”

**근거**

- 쿠폰의 적용 대상·기간·최소 결제금액·중복 가능 여부는 각각 조건부 규칙이다.
- 카드·통신사 혜택은 공식 문서에 흩어져 있고, 문서가 바뀌면 과거 조건을 그대로 믿을 수 없다.

**질문**

- “기존 카드 앱·통신사 앱과 뭐가 다른가?” → 각각의 혜택을 보여 주는 것과, 사용자가 실제 도착한 매장의 맥락에서 여러 출처의 조건을 같은 계산 규칙으로 비교하는 것은 다르다. CouponKok은 후자를 목표로 한다.
- “전월 실적·잔여 한도도 자동 계산하는가?” → 카드사 공식 연동이 없는 범위에서는 자동 확정하지 않는다. 확인된 조건만 계산하고 불확실하면 ‘공식 확인 필요’로 남기는 것이 안전하다.

### 3. Goal - AI는 설명하지만 계산은 하지 않는다

**말할 내용**

“이 프로젝트의 중심 원칙은 역할 분리입니다. Gemini와 Agent는 OCR 결과를 구조화하고, 공식 문서를 찾고, 왜 이 선택지를 제안하는지 사람이 이해할 말로 설명합니다. 하지만 최종가는 정액·정률 할인, 최소 주문금액, 최대 할인액, 중복 정책, 만료 조건을 코드로 계산하는 Calculator Tool이 확정합니다. 동일 입력에는 동일 결과가 나와야 하므로 금액 판단을 생성형 모델에 맡기지 않습니다.”

**기술 이해**

- LLM은 자연어 문서 해석과 설명에는 강하지만 수치 규칙의 재현성·감사 가능성은 보장하지 않는다.
- Calculator는 정해진 규칙과 입력만 받아 같은 결과를 반복한다.
- Agent가 Calculator의 결과를 바꾸는 것은 계약 위반이며 테스트로 막는다.

**질문**

- “그렇다면 AI가 꼭 필요한가?” → 규칙 계산 자체에는 필요 없다. 하지만 비정형 쿠폰·공식 문서의 맥락을 구조화하고, 여러 조건의 이유를 사용자 언어로 설명하며, 안전한 도구 호출을 오케스트레이션하는 데 필요하다.

### 4. CouponKok 브랜드 소개

**말할 내용**

“이 슬라이드는 사용자가 보는 제품의 정체성을 보여 줍니다. 브랜드의 목표는 할인 자체를 과장하는 것이 아니라, ‘내가 지금 실제로 쓸 수 있는 혜택’을 빠르게 확인시키는 것입니다. 따라서 UI는 초록색을 행동·확정의 포인트로 쓰고, 금액·근거·사용자 승인 단계를 분명히 분리합니다.”

**질문**

- “브랜드 로고를 왜 최소화했는가?” → 금전적 판단 화면에서는 장식보다 정보 계층, 접근성, 오사용 방지가 중요하기 때문이다.

### 5. 제품 가치 제안

**말할 내용**

“CouponKok은 세 가지 가치를 제공합니다. 첫째, 사용자가 보유한 할인·기프티콘 후보를 매장 맥락에서 좁힙니다. 둘째, 현재 위치 기반으로 필요한 순간에 알립니다. 셋째, 쿠폰 원본이 서버로 새어나가지 않도록 기기 내 OCR과 최소 전송 원칙을 적용합니다. 여기서 ‘정확하게’는 AI가 추정한다는 뜻이 아니라 공식 근거와 Calculator 규칙으로 재현한다는 뜻입니다.”

**정확한 개인정보 설명**

- 쿠폰 원본 이미지와 실제 바코드는 기기에서 관리한다.
- 서버로 보낼 수 있는 OCR 텍스트는 기기 마스킹·허용 필드 검증 뒤 DLP 재검사 경계를 거친다.
- 카드 전면은 기기 내에서 식별 단서를 추출하고, 번호·유효기간 등은 마스킹한다. 카드 뒷면 원본은 클라우드에 전송하지 않는다.

### 6. 5-Layer GCP 아키텍처

**말할 내용**

“이 그림은 Repository, Terraform, Compute, Data·Operations, Security의 다섯 층입니다. GitHub에는 코드와 선언형 인프라 정의만 둡니다. Terraform은 각 서비스 계정과 권한·리소스의 원하는 상태를 정의합니다. Compute 층은 API, ADK, MCP/동기화 Job을 책임 단위로 분리합니다. 데이터 층은 사용자 상태용 Firestore, 공식 문서·RAG 원본용 Cloud Storage, Pipeline artifact bucket으로 나뉩니다. 마지막 보안 층은 모든 서비스가 아닌 서비스별 최소 권한, Secret Manager, API·예산 관리로 구성합니다.”

**IaC 상세**

- `terraform plan`은 변경 전에 생성·변경·삭제 대상을 보여 준다.
- `terraform apply`는 승인된 차이만 반영한다.
- Secret의 실제 값은 Terraform state나 GitHub에 넣지 않는다. Cloud Run이 runtime service account로 Secret Manager에서 런타임에 참조한다.
- service account를 분리하면 API가 MCP 권한을, MCP가 사용자 Firestore 전체 권한을 가질 이유가 없어진다.

**질문**

- “왜 완전한 Kubernetes가 아닌가?” → 현재 트래픽·팀 규모에서 Kubernetes 운영 복잡도보다 Cloud Run의 scale-to-zero, 서비스별 concurrency, managed TLS·revision이 더 적합하다.
- “Terraform이 장애를 막아 주는가?” → Terraform은 구성 drift와 수동 설정 누락을 줄인다. 애플리케이션 버그, 외부 API 장애, 잘못된 데이터는 테스트·모니터링·승인 절차가 별도로 막는다.

### 7. 전체 시스템 아키텍처

**말할 내용**

“iPhone은 Vision OCR, Core Location, Keychain을 수행하고 Firebase Anonymous Auth 또는 Apple 계정 연결 구조로 사용자를 식별합니다. API는 Firebase ID Token을 검증한 뒤 필요한 요청만 Cloud Run 내부 서비스에 전달합니다. ADK Workflow는 선택적 shadow/explanation 경계입니다. MCP는 매장·공식 문서·계산처럼 외부 영향을 가진 도구를 좁은 계약으로 노출합니다. Firestore는 사용자 상태, Cloud Storage는 RAG 원문·인덱스, data.go.kr은 외부 매장 정보에 쓰입니다.”

**화살표를 읽는 법**

- iPhone → Firebase → API는 사용자 요청의 인증 경로이다.
- API → ADK의 점선은 결정론적 추천이 ADK에 완전히 의존하지 않는 선택 호출임을 뜻한다.
- ADK/MCP → Data는 최소 권한 service account로만 접근한다.
- Gemini는 계산 결과와 검증된 공식 근거를 받아 설명하며 Firestore·Cloud Storage·data.go.kr를 직접 임의 조회하거나 가격을 계산하지 않는다.

**보안 질문**

- “App Check는 enforce인가?” → 현재는 monitor 모드이며, 실기기 검증·오탐 확인 뒤 enforce로 전환하는 구조이다.
- “DLP와 Model Armor는 중복인가?” → DLP는 민감정보 탐지·마스킹에, Model Armor는 prompt injection·유해 입력 등 생성형 모델 경계 정책에 초점을 둔다.
- “실제 바코드는 어디에 있나?” → iPhone Keychain의 SecureCouponBarcodeStore에 암호화 저장하며 서버·Firebase·Gemini로 전송하지 않는다.

### 8. 병렬 Multi-Agent Flow

**말할 내용**

“현재 워크플로는 모든 Agent를 직렬로 기다리지 않습니다. 입력을 받으면 Store Agent와 Personalization Agent가 병렬로 실행됩니다. Store가 매장 맥락을 확정하면 Coupon Agent와 Benefit Agent가 병렬로 실행됩니다. 두 결과를 Join한 뒤 Recommendation Agent가 근거 설명을 만들고 Calculator MCP Tool이 최종가·절약액·가격 기준 순위를 확정합니다. 사용자는 추천을 확인한 뒤에만 바코드를 보고, 결제 후 직접 사용 처리할 수 있습니다.”

**Agent별 역할**

- **Store Agent**: 좌표·매장명 후보를 해석하고 지원 브랜드 맥락을 확인한다. 위치를 임의 추론하지 않는다.
- **Personalization Agent**: 동의된 집계 이력으로 방문 주기와 만료 위험을 설명한다. 개인의 민감 속성을 추론하지 않고 가격을 바꾸지 않는다.
- **Coupon Agent**: 등록 쿠폰에서 브랜드·만료일이 맞는 후보만 선별한다.
- **Benefit Agent**: 승인·active 상태이며 공식 출처와 유효기간이 있는 RAG 근거만 찾는다.
- **Recommendation Agent**: Calculator 결과와 공식 근거를 사용해 설명한다. 금액을 발명하거나 바꾸지 않는다.
- **Calculator MCP Tool**: 할인 규칙을 코드로 적용해 최종가·절약액·가격 기준 순위를 확정한다.

**상태 계약**

각 Agent는 `completed`, `skipped`, `blocked`, `failed`를 반환한다. 예를 들어 브랜드 일치 쿠폰이 없으면 `skipped:no_brand_match`로 즉시 종료하고 Benefit 결과만으로 가능한 안내를 이어 간다. `blocked`는 사용자 확인이나 필수 입력이 필요할 때, `failed`는 재시도로 해결되지 않은 시스템 오류에 사용한다. 이 상태 계약 덕분에 쿠폰이 없다고 전체 요청이 무의미하게 대기하지 않는다.

**중요한 질의**

- “개인화가 더 비싼 결제를 추천할 수 있나?” → 가격 기준 순위는 Calculator가 확정한다. 개인화는 표시 우선순위를 제한적으로 조정할 수 있으나, 가격 차이는 1,000원 또는 기준가의 10% 중 작은 값 이내로 제한한다. 사용자에게 최저가와 개인화 이유를 구분해 보여 준다.
- “Agent가 할인 규칙을 만들어 Calculator에 넘길 수 있나?” → 안 된다. Calculator는 활성·승인된 RAG 규칙 ID를 서버가 조회해 사용해야 하며, 임의 Agent 입력 규칙은 신뢰 경계 밖이다.

### 9. 기술 선택 원칙 - Just가 아닌 명확한 기준

**말할 내용**

“기술을 많이 쓰는 것이 목표가 아니라, 현재 단계에서 운영 복잡도와 비용을 가장 적게 하면서도 다음 단계로 교체할 수 있게 만드는 것이 기준입니다. 관리형 보안 서비스를 먼저 활용하고, 베타 트래픽에서는 세밀한 Cloud Run 제어로 비용을 관리하며, 확장 임계점이 오면 ADK Workflow·Agent Engine·pgvector 같은 대체 경로로 옮길 수 있게 합니다.”

**근거**

- 보안 서비스를 직접 구현하면 탐지 정책, 업데이트, 감사의 운영 비용이 커진다.
- 낮은 트래픽에서 항상 켜진 대규모 클러스터는 낭비가 될 수 있다.
- 인터페이스와 데이터 계약을 먼저 고정하면 런타임이나 벡터 저장소를 바꿔도 사용자 API를 덜 흔든다.

### 10. Vertex AI Agent Engine 소개

**말할 내용**

“Agent Engine은 장기 세션 상태, 배포·관찰, 멀티에이전트 실행을 더 관리형으로 제공하는 선택지입니다. 다만 이 프로젝트의 현재 선택은 Agent Engine 도입 자체가 아니라, ADK Workflow와 Tool 계약을 먼저 안정화하는 것입니다.”

**질문**

- “왜 로고를 보여 주면서 사용하지 않는가?” → 기술 후보를 검토했고 전환 기준을 명확히 하려는 슬라이드다. 현재 구현의 주력은 Cloud Run이다. ‘이미 Agent Engine으로 운영 중’이라고 말하면 안 된다.

### 11. Agent Engine vs Cloud Run

**말할 내용**

“두 서비스는 경쟁 관계라기보다 운영 단계가 다릅니다. Cloud Run은 컨테이너 단위로 API·ADK·MCP의 동시성, 메모리, 배포 revision을 세밀하게 제어하기 좋습니다. Agent Engine은 세션·자동 오케스트레이션 요구가 커졌을 때 더 적합합니다. 현재는 Cloud Run을 선택했고, Agent Engine으로 옮길 수 있는 도메인 계약을 유지합니다.”

### 12. Cloud Run 선택

**말할 내용**

“Cloud Run은 컨테이너를 그대로 실행하되 서버·노드 운영을 관리형으로 처리합니다. 요청이 없을 때 scale-to-zero로 비용을 낮출 수 있고, 각 서비스마다 concurrency를 다르게 조정할 수 있으며, revision 단위로 되돌릴 수 있습니다. 이 특성이 API·MCP·ADK라는 서로 다른 부하 특성에 잘 맞습니다.”

**용어 설명**

- **container**: 애플리케이션 코드와 실행 의존성을 이미지로 묶은 실행 단위이다.
- **revision**: Cloud Run에 새 이미지·환경 변수·설정을 반영할 때 생기는 불변 배포 버전이다.
- **concurrency**: 컨테이너 인스턴스 하나가 동시에 처리할 최대 요청 수이다. CPU·메모리·외부 모델 호출 비용에 맞춰 조정한다.
- **scale-to-zero**: 유휴 시 인스턴스 수가 0이 되는 비용 절감 방식이다. 첫 요청에는 cold start 지연이 있을 수 있다.

### 13. Cloud Run Trade-off와 Agent Engine 전환 조건

**말할 내용**

“현재 API, MCP, ADK를 서비스 책임으로 나누어 Cloud Run에 두었습니다. 장점은 이미지·동시성·권한·비용을 서비스별로 제어하는 것입니다. 단점은 장기 세션과 매우 복잡한 다중 Agent 조정은 우리가 더 관리해야 한다는 점입니다. 따라서 동시 Agent 세션 관리가 병목이 되거나 5-Agent가 N-Agent로 확장되어 자동 런타임 오케스트레이션이 필요해지면 Agent Engine을 재검토합니다.”

**질문**

- “왜 지금 Agent Engine을 쓰지 않았나?” → 현재 트래픽과 업무 복잡도에서 도입·운영 오버헤드가 이점보다 크다. 먼저 Cloud Run의 명시적 경계·관찰 가능성을 확보하는 편이 합리적이다.

### 14. 9단계 CI/CD와 롤백

**말할 내용**

“이 슬라이드는 소스에서 운영 관찰까지의 안전한 전달 경로입니다. 개발자가 main에 변경을 반영하면 CI가 lint, API/MCP 계약, Golden Test, 프롬프트·RAG 매니페스트를 검사합니다. 통과한 소스만 Cloud Build가 Docker 이미지로 만들고 Artifact Registry에 immutable digest로 저장합니다. 후보 Cloud Run revision은 health check를 받고, 사람 승인을 거친 뒤에만 트래픽을 전환합니다. 관찰 지표가 나빠지면 이전 revision으로 되돌립니다.”

**실제 범위와 주의**

- GitHub Actions의 자동 검증은 구현·확인되어 있다.
- Cloud Build 배포 정의와 Cloud Run revision 배포 경로도 있다.
- 하지만 GitHub Actions가 모든 Cloud Build·traffic promotion을 자동으로 단일 연결한 것은 아니다. staging live trajectory 평가는 수동이다.
- 따라서 “완전 자동 CD”가 아니라 **자동 품질 게이트 + 사람 승인형 후보 배포**라고 설명하는 것이 정확하다.
- ‘자동 롤백’은 revision rollback 경로를 뜻한다. 장애 지표에 의해 무조건 자동으로 운영 트래픽이 되돌아간다고 단정하려면 실제 alert→rollback 자동화와 실증 기록이 추가로 필요하다.

**질문**

- “이미지가 왜 Artifact Registry에 필요한가?” → 빌드 결과를 재현 가능한 불변 digest로 저장해 ‘내 PC에서는 됐음’ 문제를 없애고, 어느 코드가 배포됐는지 추적하기 위해서이다.
- “Prompt/RAG Gate가 왜 필요한가?” → 프롬프트·문서 변경도 모델 행동을 바꾸므로 코드 변경만큼 릴리스 통제를 받아야 한다.

### 15. 핵심 차별화 1 - Technology advancement

**말할 내용**

“첫 번째 차별화는 단순 챗봇이 아니라 Agent Pipeline, RAG, 프롬프트 버전 관리가 하나의 신뢰 경계로 연결됐다는 점입니다. 공식 문서는 candidate → reviewed/approved → active → expired/withdrawn/retired 흐름으로 관리하며, active이고 유효한 근거만 Calculator 후보가 됩니다. 프롬프트도 SHA-256 hash와 version을 매니페스트로 고정합니다.”

**질문**

- “RAG가 정확성을 보장하는가?” → 보장하지 않는다. RAG는 근거 후보를 찾는 장치이고, 출처·유효기간·권리·승인 상태를 게이트로 확인해야 한다. 숫자는 Calculator가 별도로 계산한다.

### 16. 핵심 차별화 2 - Operational automation

**말할 내용**

“두 번째는 AI 변경을 일반 코드 변경처럼 통제하는 운영 구조입니다. 프롬프트의 hash와 version을 CI, Cloud Build, 프로세스 기동 시점에 검증해 매니페스트와 다른 프롬프트가 조용히 배포되는 것을 막습니다. 혜택 문서도 제출자와 승인자를 분리하고 자동 승인 경로를 두지 않습니다.”

**정확한 표현**

- Vertex AI Pipelines는 RAG 후보·ADK release gate를 KFP v2 artifact 기반으로 검사하는 파이프라인 코드와 compile/test가 준비되어 있다.
- 실제 production 후보를 자동 승인·자동 게시하지 않는다. gate의 결과는 `blocked` 또는 `manual-review-required`이며 최종 승인은 사람이다.

### 17. 핵심 차별화 3 - FinOps

**말할 내용**

“세 번째는 기능 정확성뿐 아니라 비용·성능을 설계 대상으로 본 FinOps입니다. API, MCP, ADK의 concurrency를 다르게 두고, 매장 조회는 geo-bucket 기반 인메모리 캐시와 Firestore 영속 캐시의 2단계 캐시를 사용해 외부 공공 API 재호출을 줄입니다. Cloud Run scale-to-zero는 유휴 비용을 줄이되 cold start가 생길 수 있으므로 트래픽·SLA에 따라 min instances를 올리는 기준을 둡니다.”

**질문**

- “왜 캐시가 개인정보 문제를 만들지 않나?” → 매장 목록 캐시는 좌표를 격자화한 geo-bucket과 공공 매장 데이터 중심이며, 개인 구매 이력이나 원본 OCR을 저장하는 캐시가 아니다.
- “비용은 무엇이 가장 큰가?” → Gemini/Vertex 호출, Cloud Run CPU·메모리 시간, 외부 API 호출량, 로그·Trace·Storage가 주요 항목이다. 따라서 불필요한 Agent 호출을 skipped 처리하고, 공공 API 조회·RAG를 캐시한다.

### 18. 식별된 병목 4가지

**말할 내용**

“병목을 숨기지 않고 측정 가능한 개선 대상으로 관리했습니다. 첫째, 5-Agent를 완전 직렬로 실행하면 지연이 누적됩니다. 그래서 최신 코드에서는 Store와 Personalization, Coupon과 Benefit을 각각 병렬 Workflow로 바꾸고 상태 계약으로 불필요한 대기를 없앴습니다. 둘째, scale-to-zero의 cold start는 유휴 비용을 줄이는 대신 첫 요청 지연을 만든다는 trade-off가 있습니다. 셋째, 공공 API는 지연·rate limit이 있으므로 10분 TTL의 2단계 캐시로 완화합니다. 넷째, 작은 RAG corpus에서 Recall@5는 과도하게 좋아 보일 수 있으므로 corpus 규모와 함께 해석하고, 문서가 10만 청크 이상 또는 P95 지연이 500ms를 넘는 시점에 pgvector 같은 저장소 전환을 검토합니다.”

**현재 슬라이드 보정**

슬라이드에는 ‘Sequential 5-Agent 직렬 실행’과 ‘병렬화 검토 중’이 남아 있지만, 최신 로컬 코드는 Workflow 병렬화와 상태 계약을 구현했다. 다만 최신 ADK 워크플로가 운영 revision까지 배포되었다고 주장하려면 해당 revision 배포·health·staging 평가 기록이 필요하다. 발표에서는 “직렬 병목을 발견했고 최신 코드에서 병렬 Workflow로 해소했으며, 배포 전 staging 검증을 수행한다”라고 말한다.

### 19. 정량 지표와 정성 루브릭

**말할 내용**

“평가는 하나의 점수로 모든 것을 판단하지 않습니다. 결정론적인 Calculator·MCP 계약은 Golden Test로 정확히 일치하는지 검사합니다. 개인정보 차단은 red-team 시나리오로 검사합니다. 반면 추천 설명의 출처 투명성, 불확실성 고지, 사용자 선택권은 정성 루브릭으로 별도 검토합니다. 재현 가능한 것은 단위·계약 테스트로, 생성적 품질은 사람이 같은 기준으로 평가하는 이중 구조입니다.”

**정성 루브릭 전체**

| 기준 | 가중치 | hard gate | 의미 |
|---|---:|---:|---|
| calculator_fidelity | 0.30 | 5점 | 설명의 원가·최종가·절약액이 Calculator 결과와 정확히 일치하는가 |
| source_transparency | 0.18 | 4점 | 공식 출처·조건·확인시점이 명확한가 |
| user_agency | 0.18 | 4점 | 추천과 자동 사용을 분리하고 사용자 승인권을 보장하는가 |
| uncertainty_honesty | 0.13 | 4점 | 불확실할 때 추측 대신 확인 필요를 고지하는가 |
| privacy_clarity | 0.09 | 4점 | 수집·처리 범위를 오해 없이 설명하는가 |
| personalization_relevance | 0.07 | 4점 | 동의된 집계 이력만 사용하고 민감 특성을 추론하지 않는가 |
| actionability | 0.05 | 3점 | 사용자가 결제 직전에 다음 행동을 결정할 만큼 구체적인가 |

가중 평균 4.2 이상, 모든 hard gate 통과, 독립 검토자 3명, 검토자 간 일치율 0.8 이상을 출시 후보 기준으로 둔다.

**중요 보정**

슬라이드 오른쪽에는 calculator_fidelity 0.30과 actionability 0.05가 빠져 가중치가 0.65만 보인다. 발표에서는 위 두 항목을 반드시 말해 총합 1.00임을 보완하거나 슬라이드를 수정해야 한다. 또한 ‘RAG Recall@5 90%’는 6문서 파일셋의 제한된 결과이지 일반화된 운영 성과가 아니다.

3. “매장과 브랜드가 확인되면 Coupon Agent는 만료되지 않은 일치 쿠폰만, Benefit Agent는 공식 근거가 있는 혜택만 찾습니다.”
4. “Calculator Tool이 최종가와 절약액을 확정하고, 화면은 왜 이 선택이 가능한지 공식 출처와 조건을 보여 줍니다.”
5. “사용자가 실제 바코드를 보고 결제한 뒤 ‘결제 완료·사용 처리’를 직접 누릅니다. 자동 사용 처리는 하지 않으며, 5초 Undo와 기록 복원이 가능합니다.”

**시연 실패 대응**

- 외부 API가 느리거나 RAG 근거가 없으면 “공식 확인 필요” 또는 쿠폰 단독 Calculator 결과로 안전하게 폴백한다고 설명한다.
- 실제 바코드가 없는 데모 쿠폰은 표시용 바코드와 구분한다. 결제에 실제 사용할 수 있다고 말하지 않는다.

### 21. 성과 지표 요약

**말할 내용**

“현재 검증한 결과는 기능의 신뢰 경계를 중심으로 읽어야 합니다. Golden Test 60/60은 Calculator·MCP 계약의 결정론적 시나리오에서 통과했다는 의미입니다. 프라이버시 red-team은 정의한 마스킹·비식별화 시나리오에서 통과했다는 뜻이지, 모든 개인정보 유출 가능성이 0이라는 보장은 아닙니다. RAG Top-k=4는 검색 결과의 개수 설정이며 정확도 수치가 아닙니다. 2단계 10분 TTL 캐시는 인메모리와 Firestore 캐시 구조입니다. API 40, MCP 20, ADK 8은 서비스별 배포 concurrency 설정입니다. 5/5 SHA-256 매니페스트는 다섯 Agent 프롬프트의 hash/version이 검증된다는 뜻입니다.”

**질문**

- “60/60이면 상용화 가능한가?” → 아니며, 해당 테스트 범위의 회귀 방지 근거이다. 실제 사용자, 실제 위치 권한, 외부 문서 변화, 트래픽, 앱 심사는 별도 검증 대상이다.
- “RAG Top-k=4가 왜 성과인가?” → 성과가 아니라 운영 파라미터이다. 문서 수·질문 분포·지연을 보면서 조정해야 한다.
- “27/27은 어떤 집합인가?” → 발표 전에 실행 산출물·run ID로 그 27개를 확인해야 한다. 현재 독립 privacy guardrail eval JSON은 14개 케이스이며, 다른 단위 테스트와 합산한 값이라면 집계 근거를 제시해야 한다. 근거가 없다면 ‘정의한 개인정보 red-team 케이스 전부 통과’로 표현을 완화한다.

## 예상 핵심 질문 20개 - 짧은 답변

1. **LLM이 할인액을 계산하지 않는 이유는?** 동일 입력에 같은 수치와 감사 가능한 근거가 필요하기 때문이다.
2. **Calculator가 틀리면?** 규칙·테스트를 수정해야 하며, LLM이 보정하지 않는다. Golden Test로 회귀를 막는다.
3. **RAG가 틀리면?** 공식·active·유효한 근거만 후보로 쓰고, 없으면 계산에 반영하지 않는다.
4. **외부 API가 실패하면?** 캐시를 우선 사용하고, 그래도 근거가 없으면 안전한 폴백과 확인 필요 안내를 한다.
5. **MCP가 필요한 이유는?** Agent가 임의 네트워크·계산 권한을 갖지 않도록 허용된 Tool 계약만 사용하게 하기 때문이다.
6. **왜 외부 MCP를 직접 신뢰하지 않는가?** 금융·위치 데이터 경계에서는 API 키·응답 검증·감사를 우리 Cloud Run Adapter 경계에서 통제해야 한다.
7. **개인화 데이터는 무엇인가?** 동의된 사용 횟수·방문 주기·쿠폰 만료 위험 같은 집계이다. 카드번호, 결제내역, 민감한 특성은 수집·추론하지 않는다.
8. **개인화가 가격을 바꾸는가?** 아니다. Calculator 가격 기준 순위는 고정하고, 제한된 표시 우선순위와 이유만 제공한다.
9. **HITL이 왜 필요한가?** 추천은 결제·쿠폰 사용을 실제로 실행하지 않는다. 사용자 확인이 결제와 사용 처리의 권한 경계이다.
10. **실제 바코드가 서버에 있는가?** 없다. 기기 Keychain에 암호화 저장한다.
11. **OCR 원문을 저장하는가?** 원본 이미지는 서버에 저장하지 않으며, 전송 텍스트도 마스킹·허용 필드·DLP 검사를 거친 최소 정보만 다룬다.
12. **Firestore에 어떤 데이터가 있는가?** 사용자 프로필·구조화 쿠폰·추천/사용 기록의 최소 필드이다. 스키마와 Firestore Rules로 임의 민감 필드 쓰기를 막는다.
13. **데이터 출처는?** 매장 후보는 data.go.kr 상가(상권)정보 API와 MapKit 보완, 혜택은 공식 통신사·지원 카드 문서다.
14. **왜 MapKit도 쓰는가?** 공공 데이터의 지연·누락 시 POI 후보를 보완하기 위해서다. 공공 API 키를 iPhone에서 직접 노출하지 않는다.
15. **IaC의 실질적 이점은?** 서비스·권한·리소스 구성을 재현하고 콘솔 수동 변경 drift를 줄이는 것이다.
16. **컨테이너의 실질적 이점은?** API/ADK/MCP의 의존성을 같은 이미지로 고정하고 revision·rollback·서비스별 배포를 가능하게 한다.
17. **CI와 CD는 완전 자동인가?** 품질 검사는 자동이다. 운영 트래픽 전환과 live trajectory 평가는 사람 승인/수동 staging 경계를 둔다.
18. **왜 Agent Engine을 아직 쓰지 않는가?** 현재는 Cloud Run이 더 단순하고 비용·동시성을 제어하기 좋다. Agent 수·세션 복잡도가 임계점을 넘을 때 전환한다.
19. **Model Armor와 DLP를 모두 쓰는 이유는?** DLP는 개인정보, Model Armor는 생성형 입력·출력 안전 정책이라는 서로 다른 위험을 다룬다.
20. **가장 다음에 해야 할 일은?** 최신 병렬 Workflow를 staging에 배포하고 실제 MCP/모델 holdout, 실기기 위치·알림, 공식 문서 갱신 운영을 검증하는 것이다.
